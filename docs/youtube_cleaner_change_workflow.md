# YouTube Cleaner 變更工作流程

## 角色

這是轉接器入口步驟路由到的內部 agent 模組。使用者不需要知道這個工作流程的存在。

用於所有程式碼變更任務：bug、功能、最佳化、重構、發布、依賴升級、schema 或資料遷移、設定變更、hotfix 與清理。

此工作流程使用的技術文件（除錯、TDD、驗證）是獨立的技術文件，位於 `youtube_cleaner_techniques/`，按需讀取——永不在這裡內嵌。只讀取當前任務所需的技術文件。

## 紀律分級

每個任務開始時先判斷需要多少紀律。把力氣花在出錯代價高的地方；不要在瑣碎的工作上施加繁重流程。

- **T0——瑣碎：** 無行為邏輯變更、可逆、單一檔案（拼字、註解、常數、明顯安全的一行程式碼）。不需要除錯/TDD。一行 Before/After。跳過計劃檔案。用最相關的一項檢查來驗證。
- **T1——一般：** 範圍受控、可逆、診斷明確。輕量路徑：修復明確已確認的根本原因；在有便宜接縫處新增一個針對性測試。簡短計劃作為未 commit 草稿。類型適當的測試子集。
- **T2——困難／高風險：** 間歇性/非同步/有狀態 bug、跨模組、外部 API、不可逆、效能 regression，或你不確定的診斷。完整紀律；通常觸發決策關卡；完整驗證。

**硬性下限：** 任何不可逆、跨多模組、改變外部 API 合約或屬於遷移的變更，無論規模大小，至少為 T2——這些條件通常也會觸發決策關卡（邊界未變的跨模組工作可能不會）。

**控制：** 自動判斷分級。若使用者說「快一點」「徹底一點」（或類似指示），遵守該覆寫——但絕不低於硬性下限。

## 內部推理層

不要將此層輸出給使用者。

1. 保留使用者的原始需求。
1. 從入口步驟接收任務與已讀取的 index 摘要。
1. 選擇任務最相關的模組文件。
1. 使用上述規則判斷紀律分級（T0/T1/T2）。
1. 內部分類任務為以下任務類型之一，並引用對應技術文件，依分級調整：
   - Bug → 閱讀並遵循 `youtube_cleaner_techniques/debugging.md`（T1 = 輕量路徑，T2 = 完整回饋迴圈與排名假設）。
   - 行為變更（功能／bug 修復）且有便宜測試接縫 → 閱讀並遵循 `youtube_cleaner_techniques/tdd.md`（T0 跳過）。
   - 重構 → 套用下方重構說明。
1. 校準範圍使 Before/After 準確：什麼會改變、哪些下游可能受影響、哪些邊界仍不確定。
1. 檢查是否有決策關卡觸發條件（見下方）。若有，在 Before/After 之前使用決策關卡。

## 內部任務類型

挑選恰好一種類型。每種類型標明工作內容、宣稱完成前預期的最低驗證、以及回滾路徑。驗證指令是專案特定的——挑選本專案中存在的指令（`package.json`、`CONTRIBUTING.md`、CI 設定或同等）。

- **Bug**：目前行為錯誤或不穩定。在提出根本原因前，先透過 `youtube_cleaner_techniques/debugging.md` 調查；T2 時此為強制。驗證：重現消失；相關測試通過。回滾：還原修補。
- **功能**：新行為。驗證：新測試覆蓋 happy path 與一個失敗路徑；建置與型別檢查通過。回滾：功能開關或還原。
- **最佳化**：相同行為，更好品質。驗證：現有測試通過；目標指標前後測量。回滾：還原至先前基準線。
- **重構**：結構變更，行為不變。驗證：完整測試套件通過；公開 API 不變，除非明確納入範圍。回滾：還原。
- **發布**：版本號、變更日誌、標籤。驗證：manifest 與 changelog 一致；產出物乾淨建置；標籤遵循專案慣例。回滾：刪除標籤並還原版本號。
- **依賴**：升級/降級/替換/移除套件。驗證：安裝或 lockfile 重新產生成功；建置通過；覆蓋呼叫者的測試通過；檢查 release notes 中的 breaking change。回滾：固定至先前版本。
- **遷移**：schema、資料或儲存遷移。驗證：在乾淨副本上前向遷移成功；存在反向腳本或記錄不可逆性；遷移後一個讀取路徑和一個寫入路徑被執行。回滾：反向腳本或從快照還原。一律升級至決策關卡。
- **設定**：環境變數、功能開關、基礎設施設定、執行期參數。驗證：設定在受影響環境中載入；相依路徑回應；無密鑰提交。回滾：還原值；重新載入程序。
- **Hotfix**：線上事故的緊急修復。驗證：最小重現消失；修補分支上套件仍通過；記錄後續任務。回滾：還原；偏好最小變更面。
- **清理**：死碼、合併、未使用資源移除。驗證：建置與完整套件通過；移除的符號無剩餘引用；行為不變。回滾：還原。

若任務無法乾淨匹配一種類型，挑選最接近的並在內部記錄偏差。不要發明新型別。

### 重構說明

重構時，目標是深化：更多行為藏在更小、更可測試的介面後。對任何你懷疑是淺層透傳的事物套用刪除測試——想像刪除它：若複雜度消失，它一無所獲；若複雜度重新出現在它的呼叫者中，它正在發揮作用。改變結構，永不改變行為，全程保持完整套件綠色。

## 外部報告層

1. 若有決策關卡觸發條件匹配，先呈現決策關卡格式並等待使用者選擇。
1. 使用下方 Before / After 格式與使用者確認。
1. 等待使用者明確確認後才編輯任何檔案。
1. 記錄計劃，依分級調整——這是工程草稿，不是使用者面向的確認。計劃檔案放在兩個資料夾中：尚未實作的計劃放在 `docs/changes/planning/`，已完成的放在 `docs/changes/completed/`。`{{DATE}}` 和 `{{SLUG}}` 在這裡按每次變更填入；它們不是初始化佔位符：
   - T0：跳過計劃檔案。
   - T1：寫入 `docs/changes/planning/{{DATE}}-{{SLUG}}.md`（必要時建立資料夾），包含以下欄位——任務類型、已確認的 Before、已確認的 After、預期檔案範圍、驗證步驟、回滾路徑。保留為未 commit 草稿。在此檔案存在前不要編輯原始檔。
   - T2：寫入相同的計劃檔案（也放在 `docs/changes/planning/`）。若交付策略允許 commit（`commit only` / `commit and push`），在編輯原始檔前執行 `git add docs/changes/planning/{{DATE}}-{{SLUG}}.md` 和 `git commit -m "plan: {{SLUG}}"`；在 `no commit` 下，保留為未 commit。在此檔案存在前不要編輯原始檔。
1. 實作變更。
1. 閱讀並遵循 `youtube_cleaner_techniques/verification.md` 進行驗證，依分級調整。將驗證結果納入使用者面向報告。若驗證失敗，不要宣稱完成：修復並重新驗證，或誠實報告失敗並詢問如何繼續。
1. 驗證通過且變更真正完成後，將計劃檔案從 `docs/changes/planning/` 移至 `docs/changes/completed/{{DATE}}-{{SLUG}}.md`（保持相同名稱；必要時建立資料夾）。若此次僅產出計劃未實作（例如使用者延後，或為設計面談產出），將計劃留在 `docs/changes/planning/`。
1. 用一句白話結束，描述變更了什麼以及如何驗證。

## 報告規則

- Before / After 是唯一的人機確認介面。
- 本專案的報告層級：白話
  - 白話：不在使用者面向的報告中暴露模組名稱、檔案路徑、函式名稱或程式碼片段。
- 內部推理與使用者面向摘要保持分離。
- 驗證狀態是使用者面向報告的一部分，無論報告層級：白話陳述檢查是否通過、跳過或失敗。

## Before / After 格式

**Before**：用一到三句白話，解釋目前狀況與診斷出的問題——哪裡錯了、缺少了什麼或有風險，以及你對根本原因的判斷。使用者在此處判斷你的診斷；若膚淺或錯誤，這是他們抓到的時機。

**After**：用一到三句白話，解釋變更後會變成什麼樣子，以及如何驗證。

等待使用者明確確認後才進行任何檔案編輯操作。

## 決策關卡

決策關卡是 Before / After 的升級版，用於影響範圍較廣的變更。當任何觸發條件匹配時使用：

- 變更會改變模組邊界（建立、移除或合併模組）。
- 變更影響外部 API 合約或公開介面。
- 有兩個以上可行方案且取捨不同。
- 變更涉及不可逆操作（大規模刪除、資料庫遷移、框架替換、含資料遺失的套件降級）。
- 內部任務類型為遷移或包含不可逆步驟。

當決策涉及多個互相依賴的未解決決策或不明確的需求——而非乾淨的 A/B——先透過 `youtube_cleaner_techniques/design-grilling.md` 解決：一次面試一個問題，每個附帶建議答案，在可能時探索 atlas 與程式碼來回答。然後呈現下方選項。

觸發時，呈現此格式取代 Before / After：

```markdown
## 決策：<一句話標題>

### 脈絡
為什麼需要這個決策。

### 選項
A. <選項 A> — <優點 / 代價>
B. <選項 B> — <優點 / 代價>

### 影響
哪些區域受影響以及如何受影響。
```
